# 항공권·자유여행 특가 알리미

싸게 나온 항공권과 여행사 자유여행 상품을 찾아 텔레그램으로 알려준다.
어디서 사는지 링크도 같이 보낸다.

## 무엇을 걸러 주나

**싸다는 건 그 노선의 평소 가격과 비교해서 정한다.** 절대 금액이 아니다.
기준선을 셋 쓰고, 하나만 걸려도 알린다.

| 기준 | 무엇을 잡나 | 자료 |
|---|---|---|
| 평소 가격(중앙값) 대비 **-25%** | 비싼 날짜들 사이에 끼어 있는 싼 날 | Travelpayouts |
| 최근 7일 **최저가** 대비 **-20%** | 노선 전체가 갑자기 떨어진 순간 | Travelpayouts |
| **같은 달 평소가 대비 -30%** | 네이버 가격그래프에서 눈에 띄게 낮은 막대 | 네이버 |
| **임박: 정상 구간 평소가 대비 -25%** | 코앞인데도 평소만큼 싼 자리 | 네이버 |

두 번째는 스카이스캐너 Drops와 같은 방식이다. Drops는 앱 전용이라 가져올 API가
없어서 규칙만 옮겨 왔다. 이미 싼 값이 기준이라 같은 퍼센트라도 훨씬 넘기 어렵고,
그만큼 걸리면 신호가 강해서 알림 순위를 올려 준다.

세 번째가 네이버 경로다. 네이버는 목적지 한 곳당 한 번만 물으면 **앞으로 1년치
날짜별 최저가**를 통째로 준다. 그 안에 '같은 달 다른 날짜들'이 다 들어 있어서
**과거 이력 없이도 그 자리에서 평소값을 낸다.** 비교는 같은 목적지·같은 출발월·
같은 일수·직항 여부가 같은 표들끼리만 한다(3일과 14일을 섞으면 안 되므로).

40% 이상이면 🔥 대박으로 표시한다.

**여행 기간을 거리로 정한다 — 단, Travelpayouts 경로에서만.** 인천에서 4,500km
안쪽(일본·동남아·대만 등)은 2~4일 왕복, 그 바깥(미주·유럽·호주 등)은 7~14일 왕복.
⚠**네이버 경로는 이 규칙을 안 건다(2~14일 전부 본다).** 근거리를 2~4일로 묶어
보다가 싼 값을 통째로 놓치고 있었기 때문이다. 실측(2026-08-15):

| 목적지 | 전체 최저가 | 2~4일로 한정하면 |
|---|---|---|
| 도쿄 | 182,235원(14일) | 233,666원 |
| 삿포로 | 264,342원(7일) | 361,840원 |
| 웨이하이 | 179,757원(13일) | 495,347원 |

**국내선은 보지 않는다.** 해외 왕복을 찾는 물건이다.

**임박 특가(모레~2주 뒤 출발)도 본다.** 다만 기준이 다르다. 임박 구간은 남은
날짜가 전부 임박이라 '같은 달 평소가'를 낼 수 없다 — 비교 상대가 다 같이 비싸서
임박 프리미엄이 통째로 기준선에 섞인다. 그래서 **리드타임 바깥 정상 구간의
평소값**과 견준다. "코앞인데도 평소만큼 싸다"가 진짜 임박 특가다. 제목에 ⏰가 붙고,
출발까지 며칠 남았는지 같이 적어 준다. 오늘·내일 출발은 안 본다(알림을 받아도 못 간다).

**갔을 때 날씨가 나쁘면 안 알린다.** Open-Meteo에서 최근 3년 실측 자료를 받아
목적지별·월별 평년값을 직접 계산한다. 우기·폭염·혹한기는 점수가 깎여 걸러진다.
설경이 목적인 곳(삿포로 등)은 추위 벌점을 절반만 준다. 하한은 60점이다.

**임박 구간만 하한이 45점이다.** 임박은 갈 수 있는 날이 며칠 안 돼서 60점을
그대로 대면 사실상 아무것도 안 뜬다. 실측(2026-08-16, 25개 목적지): 정상가보다
25% 넘게 싼 임박 표가 여럿이었는데 8월 말 일본이 폭염·우기라(후쿠오카 27점·
오사카 12점·오키나와 10점) **60점에서 전량 탈락**했다. 하한별 결과는
60점 0건 · 45점 1건 · 30점 3건 · 하한 없음 11건. 45점이면 장마·태풍철
최악(오키나와 10점·마카오 0점)은 여전히 걸러진다.

**여행사 자유여행 특가도 같이 본다.** 웹투어·모두투어·온라인투어의 상품 목록을
읽어 같은 목적지·같은 일수 상품들과 비교한다.

## 시작하기

```bash
pip install -r requirements.txt
copy .env.example .env      # 값을 채운다
python main.py warmup       # 기후 자료를 미리 받아둔다 (한 번만, 몇 분 걸림)
python main.py test         # 텔레그램 연결 확인
python main.py loop         # 6시간마다 계속 돌린다
```

### 토큰 두 개

| 무엇 | 어디서 | 필수 |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | 텔레그램에서 `@BotFather` → `/newbot` | 알림 받으려면 필요 |
| `TRAVELPAYOUTS_TOKEN` | travelpayouts.com 무료 가입 → Flight Data API | 항공권 보려면 필요 |

`AMADEUS_CLIENT_ID` / `SECRET`은 선택이다. 넣으면 알림 보내기 직전에 실시간
가격으로 한 번 더 확인해서, 이미 팔린 가격을 거르고 보낸다.

**여행사 특가는 키가 하나도 없어도 된다.** `python main.py packages` 로 바로 확인할 수 있다.

### 알림 받을 사람 등록

`.env`의 `TELEGRAM_CHAT_ID`를 비워 두고 `python main.py listen` 을 켠 다음
봇에게 `/start` 를 보내면 자동 등록된다.

## 어디서 도는가

**깃허브가 대신 돈다**(`.github/workflows/scan.yml`). 내 컴퓨터가 꺼져 있어도
알림이 온다. 토큰은 저장소가 아니라 깃허브 금고(Settings → Secrets)에서 읽는다.

| | 내 PC(작업 스케줄러) | 깃허브 Actions |
|---|---|---|
| 컴퓨터 꺼져 있을 때 | 안 돎 | **돎** |
| 시각 정확도 | 정확 | 5~30분 늦을 수 있음 |
| 가격 이력 | 그냥 파일에 쌓임 | 매 실행마다 저장소에 되커밋 |

깃허브 서버는 실행이 끝나면 흔적을 지운다. 그래서 `data/deals.db`를 저장소에
되돌려 커밋한다. 이게 없으면 '평소 가격'을 영영 못 쌓아 딜 판정이 안 된다.

**둘을 같이 돌리지 마라.** 가격 이력과 발송 이력이 따로 놀아서 같은 딜이 두 번 온다.

## 왜 하루 두 번, 왜 그 시각인가

**여행사는 영업시간이 있다.** 하나투어 타임세일이 매주 월요일 오전 10시로 확인된다.
상품 등록은 업무 시작 후 오전 중에 몰린다. 그래서 **10:30**에 한 번 본다.

**항공권은 영업시간이 없다.** 항공사 동적 가격은 24시간 알고리즘으로 움직이고,
스카이스캐너 Drops도 매시간 갱신한다. 다만 "화요일 오후~수요일 새벽에 항공사가
남은 좌석에 프로모션 요금을 건다"는 통설이 있어 그 직전인 **22:30**에 한 번 본다.
밤 늦어도 사람이 바로 예약할 수 있는 시간대이기도 하다.

**이 두 시각은 출발점일 뿐 근거가 반쪽이다.** 오전 10:30은 확인된 사실에 기댄
것이지만 22:30은 통설이다. 그래서 봇이 직접 재도록 해 뒀다.

```bash
python main.py hours
```

노선별로 직전까지의 최저가를 깬 순간만 골라 그 시각을 세어 막대로 보여 준다.
2~3주 돌린 뒤 이걸 보고 `.env`의 `SCAN_TIMES`를 실제 데이터에 맞춰 고치면 된다.

## 알아 둘 것

**여행사 상시 할인 10%는 특가가 아니다.** 실측해 보니 웹투어 상품 대부분이
정가 대비 정확히 10% 할인으로 붙어 있다. 그래서 정가 대비 할인율만으로는
파격을 못 가린다. 같은 목적지·같은 일수 또래 상품과 비교하는 쪽이 진짜 신호다.

**여행 일수를 나눠서 비교한다.** 오사카 3일과 오사카 5일을 같이 놓으면
3일짜리가 무조건 싸 보인다. 제목에서 일수를 뽑아 3일 이하 / 4~5일 / 6~7일 /
8일 이상으로 나눈 뒤 같은 묶음 안에서만 비교한다.

**숙박 전용 상품은 뺀다.** `룸 ONLY` 처럼 항공이 빠진 상품을 에어텔과 비교하면
반값으로 보인다. 제목에서 걸러 낸다.

**한 달에 두 번씩 묻는다.** Travelpayouts는 '출발 달'과 '귀국 달'을 따로 받는데,
둘을 같은 달로 주면 달을 넘겨 돌아오는 일정이 결과에서 통째로 빠진다. 겹치지도
않아서 한 번만 물으면 그만큼을 영영 못 본다. 실측으로 방콕 9월은 26건 중 11건이
그랬고, 후쿠오카·방콕·다낭은 **최저가가 전부 달을 넘기는 일정**이었다.
그래서 매달 (같은 달 귀국)과 (다음 달 귀국)을 각각 묻고 합친다.

**공항 코드는 바뀐다.** 신공항이 열리면 옛 코드가 죽는다. 씨엠립은 `REP`→`SAI`
(2023년), 울란바토르는 `ULN`→`UBN`(2021년)으로 바뀌어 있었다. 이런 건 그 목적지만
조용히 빠지고 총계는 멀쩡해 보여서 알아채기 어렵다. 반년에 한 번쯤 돌려서 확인해라.

```bash
python _smoke_airports.py
```

**여행사 사이트는 개편이 잦다.** 어떤 여행사에서 상품을 0건 읽으면 조용히
넘어가지 않고 "구조 변경 의심" 경고를 텔레그램으로 보낸다. 그때 `packages.py`의
해당 파서를 고치면 된다.

**멀리 볼수록 자료가 얇아진다.** 8개월치를 훑지만 API가 가진 양이 뒤로 갈수록
급격히 준다. 실측(2026-08-14 기준):

| 출발월 | 9월 | 10월 | 11월 | 12월 | 1월 | 2월 | 3월 |
|---|---|---|---|---|---|---|---|
| 관측 | 1,652 | 1,020 | 508 | 507 | 55 | 18 | 13 |

5개월(12월까지)에서 8개월로 늘려 얻은 건 86건뿐이다. 그래도 두는 이유는,
유럽·미주 봄여름 특가가 바로 그 구간에 풀리기 때문이다. 한 번 걸리면 크다.
늘리는 값은 스캔 시간 3분(5분→8분)이고 깃허브 실행 시간은 공개 저장소라 무제한이다.

**네이버 경로에도 같은 함정이 있고, 여기선 더 고약하다.** 먼 달은 네이버가 가진
표가 몇 장 없어서 그 달의 중앙값이 위로 튄다. 그러면 멀쩡한 값이 엄청난 특가로
둔갑한다. 실제로 2027년 8월 하노이가 '평소 120만원'으로 잡혀 37만원짜리가
**-69% 특가**로 올라왔다. 그래서 두 겹으로 막는다.

- 같은 무리가 **8건 미만이면 평소값을 말하지 않는다**(일수 버킷으로 한 번 넓혀 보고,
  그래도 얇으면 판정 자체를 안 한다).
- 달 기준값이 **노선 전 기간 중앙값의 1.6배를 넘으면 버린다**(`NAVER_MAX_BASELINE_RATIO`).

이 두 가드로 66건 → 28건이 됐다. 걸러진 38건은 전부 표본이 얇은 먼 달이었다.

```bash
python _smoke_naver.py      # 질의가 아직 먹히는지, 가드가 도는지
```

**네이버 API는 까다롭게 군다.** 두 가지를 지켜야 한다. 안 지키면 조용히 0건이 된다.

- **POST는 nginx가 503으로 막는다.** GET(쿼리스트링)으로 물어야 한다.
- **`x-apollo-operation-name` 헤더가 없으면 CSRF로 보고 전부 거부한다.**
  이걸 빠뜨려 81곳 전량 0건이 나온 적이 있다. 워크플로는 "성공"으로 끝난다.

**네이버 관측은 DB에 안 쌓는다.** 한 번에 19,000건씩 오는데 그대로 저장하면
매 실행마다 저장소에 되커밋하는 DB가 하루 만에 몇 배로 불어난다. 이 경로는
판정에 이력이 필요 없어서 안 쌓아도 된다.

**첫 실행에는 항공권 딜이 거의 안 나온다.** 평소 가격을 알아야 싼지 판단할 수
있는데, 노선당 관측이 8건은 쌓여야 비교를 시작한다. 며칠 돌리면 정확해진다.
여행사 특가는 또래 비교라서 첫 실행부터 작동한다.

**며칠씩 조용한 게 정상이다.** 파격가는 원래 드물다. 실제로 어느 날 자유여행 상품
164건을 훑어도 -25% 넘는 게 하나도 없었고(최대 -17.7%), 그게 맞는 동작이다.
살아 있는지 확인하려면 `/status`(마지막 스캔 시각)나 `python main.py packages`를 보면 된다.
후자는 기준에 못 미친 상위권까지 같이 찍어 준다.

**그래도 스캔은 자주 한다.** 훑는 주기(6시간)와 알리는 문턱(-25%)은 별개다.
파격가는 몇 시간이면 사라져서, 하루 한 번만 보면 이미 팔린 뒤에 발견하게 된다.

**알림이 너무 없으면** `.env`에서 `DEAL_DROP_PCT` / `PACKAGE_DROP_PCT`를 15~20으로
낮추거나 `MIN_WEATHER_SCORE`를 50으로 내려라. 너무 많으면 반대로 올리면 된다.
